## 1. F22 속도 개선

### 1.1 측정 방법
- 데이터: .NET 런타임과 SDK 폴더 복사본 (파일 5,066개, 828MB, DLL·텍스트·설정 파일이 섞인 실제 파일)
- 반디집 7.39 명령줄(`bz.exe`)과 같은 수준(빠르게 1 / 보통 5 / 최고 9)으로 비교
- PC: Intel i7-9700 (8코어), 다른 작업 없이 측정

### 1.2 1.0.0 결과

| 형식·수준 | 또또집 | 반디집 | 판단 |
|---|---|---|---|
| ZIP 빠르게 | 19.4초, 350MB | 21.6초, 371MB | 이미 더 빠르고 작음 |
| ZIP 보통 | 19.7초, 334MB | 21.7초, 345MB | 이미 더 빠르고 작음 |
| ZIP 최고 | **99.3초**, 328MB | 44.8초, 341MB | 2.2배 느림 |
| 7Z 빠르게 | 20.6초, 274MB | 24.0초, 266MB | 빠르지만 3% 큼 |
| 7Z 보통 | **65.4초, 220MB** | 52.5초, 190MB | 느리고 16% 큼 |
| 7Z 최고 | 94.0초, **196MB** | 97.0초, 179MB | 비슷한 속도, 10% 큼 |

결론: 압축 엔진은 같은데 **엔진 설정**이 달라서 생긴 차이. 프로그램 구조(파일 읽기, 진행률 등)는 원인이 아님 (ZIP은 이미 더 빠름).

### 1.3 원인과 해결

| 원인 | 설명 | 해결 | 효과 (7Z 보통) |
|---|---|---|---|
| 파일 순서 | 7Z는 파일을 이어 붙여 한꺼번에 압축하는데, 1.0은 이름순으로 넣음. 같은 종류(DLL끼리, 텍스트끼리)를 모으면 더 잘 줄고 빨라짐 | 7Z에 "종류별 정렬"(`qs`) 켜기 | 70.2초 220MB → **58.0초 181MB** |
| 실행 파일 필터 | DLL·EXE는 기계어 주소를 바꿔 주면 더 잘 줄어듦 | `BCJ2` 필터 (실행 파일에만 적용) | → 54.6초 181MB |
| ZIP 최고 | 7-Zip의 ZIP 최고 수준(9)은 같은 데이터를 여러 번 다시 훑어서, 크기는 1-2%밖에 안 줄면서 시간이 2배 넘게 듦 | ZIP 최고를 엔진 수준 7로 | (ZIP 최고) 99.3초 → **40.9초**, 328 → 330MB |

`BCJ2`는 7Z 보통에서만 3초 빨랐고 빠르게·최고에서는 효과가 없거나 오히려 느려서 넣지 않음 (7-Zip은 기본으로 실행 파일 필터를 이미 적용함).

### 1.3.1 바꾼 뒤 예상 결과

| 형식·수준 | 1.0.0 | 1.1 (새 설정) | 반디집 |
|---|---|---|---|
| ZIP 빠르게 | 19.4초, 350MB | (그대로) | 21.6초, 371MB |
| ZIP 보통 | 19.7초, 334MB | (그대로) | 21.7초, 345MB |
| ZIP 최고 | 99.3초, 328MB | **40.9초, 330MB** | 44.8초, 341MB |
| 7Z 빠르게 | 20.6초, 274MB | **14.1초, 264MB** | 24.0초, 266MB |
| 7Z 보통 | 65.4초, 220MB | **58.0초, 181MB** | 52.5초, 190MB |
| 7Z 최고 | 94.0초, 196MB | **82.0초, 177MB** | 97.0초, 179MB |

- 크기는 6가지 모두 반디집보다 작고, 속도는 7Z 보통만 반디집보다 약 10% 느림
- 새 설정 값은 한 번씩 잰 결과. 같은 설정도 측정마다 5-10% 차이가 있어서(7Z 보통 기준 65-70초), 4단계에서 3번씩 다시 재서 확정
- 7Z 보통을 더 빠르게 할 방법(스레드 나누기 단위 등)은 4단계에서 더 찾아봄

### 1.4 바꾸는 곳
- `Compressor.BuildProperties`: 7Z에 종류별 정렬(`qs=on`) 추가, ZIP 최고를 엔진 수준 7로
- 명령줄 `ddz a --engine 이름=값`: 숨은 옵션. 설정을 바꿔 가며 재는 용도 (사용법 안내에는 넣지 않음)
- 자동 테스트: 새 설정으로 만든 7Z·ZIP을 반디집과 또또집 양쪽에서 검사
- 속도 측정 스크립트를 `tools/benchmark.ps1`로 저장소에 넣어, 버전마다 같은 방법으로 비교

### 1.5 함께 하는 것
- **큰 TAR.GZ 열기**: 안의 TAR를 꺼내는 동안 진행률 창을 띄우고 취소할 수 있게 함
- **파일 10만 개 목록**: 목록 트리를 화면 스레드 밖에서 만든 뒤 한 번에 표시

## 2. F20 자동 업데이트

### 2.1 확인
- 주소: `https://api.github.com/repos/dukdo2/DdoddoZip/releases/latest` (로그인 없음, 공개 정보)
- 받는 것: 버전(`tag_name`, 예: `v1.1.0`), 설치 파일 이름·주소·크기, **SHA-256 해시**(`digest`)
  - 2026-11-17 1.0.0 릴리스로 확인: 해시가 실제 파일과 같음
- 보내는 것: 프로그램 이름이 든 User-Agent 하나 (GitHub API 필수). 사용자 정보·PC 정보 없음
- 시점: 메인 창이 뜬 뒤 뒤에서, 마지막 확인 후 24시간이 지났을 때만. 우클릭 명령으로 실행될 때는 확인하지 않음
- 실패(인터넷 없음, GitHub 응답 없음, 한 시간 60번 제한)는 조용히 넘어감

### 2.2 안내
- 메인 창 위에 띠: "또또집 1.1.1이 나왔습니다. [업데이트] [이 버전 건너뛰기] [닫기]"
- "이 버전 건너뛰기"를 누르면 그 버전은 다시 알리지 않음 (설정에 저장)
- 정보 창에 [업데이트 확인] 버튼과 "자동으로 확인" 체크 상자 (기본 켜짐)

### 2.3 받기와 설치
1. `%TEMP%\DdoddoZip\update\`에 받음 (진행률 창, 취소 가능)
2. 받은 파일의 SHA-256이 GitHub가 알려 준 값과 같은지 확인. 다르면 지우고 오류 안내
3. 설치 파일을 `/SILENT /UPDATE` 로 실행하고 또또집은 종료
4. 설치 파일이 끝나면 또또집을 다시 엶 (설치 스크립트에 `/UPDATE`일 때만 실행하는 항목 추가)
5. 관리자 확인 창(UAC)은 설치 파일이 띄움 (지금과 같음)

### 2.4 안전 장치
- 주소는 프로그램 안에 고정 (`dukdo2/DdoddoZip`). 다른 저장소나 주소로 바뀌지 않음
- 설치 파일 주소는 `https://github.com/dukdo2/DdoddoZip/releases/download/`로 시작할 때만 받음
- 해시 확인은 "받는 중에 깨지거나 바뀐 파일"을 막음. **GitHub 계정 자체가 털리면 막지 못함**: 이를 막으려면 코드 서명이 필요 (유료, 1.1 범위 밖)
- 버전 비교는 숫자로 (1.10 > 1.9). 초안·시험판(prerelease) 릴리스는 무시

### 2.5 바꾸는 곳
| 파일 | 내용 |
|---|---|
| `App/Services/UpdateService.cs` (새 파일) | 확인, 받기, 해시 확인, 설치 실행 |
| `App/MainWindow.xaml` | 업데이트 띠 |
| `App/Views/AboutWindow` (새 창) | 버전, 업데이트 확인, 후원, 라이선스 |
| `App/Services/Services.cs` | 설정에 마지막 확인 시각, 건너뛴 버전, 자동 확인 여부 |
| `installer/DdoddoZip.iss` | `/UPDATE`일 때 설치 후 또또집 다시 열기 |

## 3. F23 후원

- 메인 창 도구 모음 오른쪽 끝에 작은 **[♥ 후원]** 버튼 → 정보 창의 후원 부분을 엶
- 정보 창에 두 가지: **카카오페이로 후원** (송금 링크), **GitHub Sponsors** (`https://github.com/sponsors/dukdo2`)
- 링크는 한 곳(`SupportLinks` 상수)에만 둠. 아직 링크가 없으면 그 버튼은 숨김
- 저장소에 `.github/FUNDING.yml` 추가 → GitHub 저장소 페이지에 "Sponsor" 버튼

### 사용자가 해야 할 것
1. 카카오페이 앱에서 송금 코드(링크) 만들기 → 링크 전달
2. GitHub Sponsors 가입·심사 신청 (github.com/sponsors) → 승인되면 알려 주기
